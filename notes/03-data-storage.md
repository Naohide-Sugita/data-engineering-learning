## 3-1. Cloud Storage

### データ形式と圧縮
- 行指向：CSV、JSON
- 列指向：Parquet、ORC
- Parquetなどの列指向形式は分析時に必要な列だけ読み込みやすい
- SnappyはParquetなどと組み合わせて利用される圧縮方式の1つ

### 基本構造
- バケット：オブジェクトを格納するコンテナ
- オブジェクト：保存されるファイルデータ
- Cloud Storageはオブジェクトストレージ
- `/` 区切りの名前を使ってフォルダのように見せることができる

### メタデータ
- オブジェクトには作成日時、更新日時、コンテンツタイプなどのメタデータを保持できる

### ライフサイクル管理
- 条件に応じてストレージクラス変更や削除を自動化する
- 「90日後にColdline」「1年後に削除」など、明確なルールがある場合に向く

### Autoclass
- 実際のアクセスパターンに応じてストレージクラスを自動最適化する
- アクセス頻度を事前に予測しにくいデータに向く

**使い分け**
- 明確な日数・保持ルールあり → ライフサイクル管理
- アクセスパターンが読めない → Autoclass

### バージョニング
- オブジェクトの過去バージョンを保持できる
- 誤更新・誤削除からの復旧に利用できる

### 保持・ロック
- 保持ポリシーなどで一定期間オブジェクトを削除・変更できないようにできる
- コンプライアンス要件などで利用する

### 署名付きURL
- 限定された期間・操作だけCloud Storageオブジェクトへのアクセスを許可するURL

### アクセス制御
- IAM：Google Cloud標準のアクセス制御
- ACL：オブジェクト単位などの従来型アクセス制御
- 通常はUniform bucket-level accessを使い、IAMで一元管理する

### コマンドライン操作
- `gcloud storage` などでバケットやオブジェクトの一覧、コピー、アップロード、削除を実行できる
- 大量データでは並列処理により転送効率を上げられる

## 3-8. ストレージ方式の使い分け

### データ種類・用途
- 非構造化ファイルを保存する → Cloud Storage
- 構造化データをSQLで大規模分析する → BigQuery
- アプリケーションから小さなドキュメントを頻繁に読み書きする → Firestore
- 大量データを低レイテンシ・高スループットでKey-Value的に扱う → Bigtable
- 一般的なRDB/OLTP → Cloud SQL

Firestoreの例：
- SNSの投稿
- コメント
- プロフィール
- 通知

### 分析・ML向け
- BigQuery上で分析・MLを行う構造化データ → BigQuery
- 画像・音声・動画などの非構造化ファイル → Cloud Storage
- ストリーミングデータを分析基盤へ蓄積 → BigQuery

### Cloud Storageのストレージクラス
- Standard：頻繁にアクセス
- Nearline：月1回程度
- Coldline：数か月に1回程度
- Archive：ほとんどアクセスしない長期保管

「月1回程度アクセス + 低コスト + すぐ取得」→ Nearline

## 3-9. リージョン / マルチリージョン等の配置

### リージョン
- 1つのリージョンにデータを配置する
- 処理するサービスと同じリージョンに置くとレイテンシを抑えやすい

### デュアルリージョン
- 指定した2リージョンにデータを配置する
- 保存先を明確にしつつ可用性を高めたい場合に向く

### マルチリージョン
- 広い地理範囲の複数リージョンにまたがってデータを配置する
- 広域で利用するデータや高い可用性が必要な場合に向く

### レイテンシ
- リクエストしてから結果が返るまでの待ち時間
- 一般に、処理する場所とデータの場所が近いほど低くしやすい
